# Известные ограничения

<!-- l10n: source=reference/known-limitations.md source-sha256=005074ec3caf17e2c206f7d659c5a2cf975a19e91d01ba4a6c6bd197777e658b -->
> Перевод [исходной страницы на английском языке](../../../reference/known-limitations.md) для OmsiLaunch 0.1.0-beta4. Нормативной является английская страница: при расхождениях приоритет имеют английская страница и код.

На этой странице по коду перечислено всё, что в OmsiLaunch 0.1.0-beta4 имеет статус `UNAVAILABLE`, `PARTIAL` или является принятым риском, чтобы пользователи и интеграторы не опирались на поведение, которого продукт не обеспечивает. В каждой строке указаны ограничение, его стабильность, причина его существования и место, где оно описано подробно. Нормативной является английская документация; локализованные копии в `docs/localized/` не поддерживаются на том же уровне и могут отставать (см. последний раздел).

| В runtime проверена только известная раскладка; определение, не зависящее от сборки, проверено офлайн по эталонному исполняемому файлу с удержанной идентичностью | `EXPERIMENTAL` на неизвестных сборках | [статус проверки в runtime](../status/runtime-validation-status.md) |
| Только Windows 10+ x64; нет поддержки Windows 7/8, XP и ARM64 | `UNAVAILABLE` | [совместимость](compatibility.md) |
| Плагину нужна среда выполнения .NET 6 **x86** в дополнение к среде выполнения x64, которую использует контроллер | | [совместимость](compatibility.md) |

| Ограничение | Стабильность | Подробности |
| --- | --- | --- |
| `LAST_MAP_STATE` (`/last /map:<identity>`) реализован по статическому анализу ветки последнего состояния OMSI и проверен только офлайн | `EXPERIMENTAL` | [CLI](cli.md) |
| Явные или системные дата, время и год (`/date`, `/time`, `/year`, `new.date`/`new.time`/`new.year` профиля) применяются только при запуске NEW_MAP и проверены офлайн; проверка в runtime ожидается. 31 декабря високосного года запросить нельзя (календарь OMSI переходит через день 366) | `EXPERIMENTAL` | [launchspec](launchspec.md#datespec-timespec-yearspec) |
| Пресет погоды, ICAO и текущая реальная погода при запуске (`/weather*`, `new.weather`) применяются сразу после запуска мира через собственную загрузку погоды OMSI и флаги METAR (закрыто статически, BI-003); проверка в runtime ожидается. Погода, которую OMSI показывает в самом первом кадре, всё ещё может быть погодой карты по умолчанию | `EXPERIMENTAL` | [CLI](cli.md) |
| Модель транспортного средства игрока, окраска, HOF, бортовой номер и регистрационный номер при запуске (семейство `/vehicle`, `PlayerVehicleSpec`) разрешаются по каталогу контента, но не применяются; их запрос делает план неисполнимым. Нативная последовательность назначения (размещение через диалог позиции OMSI, `MakeVehicle`, завершающие шаги для каждой единицы, `CopyTempListIntoMainList`, индекс игрока) закрыта статически, но создаёт и регистрирует живое ТС и не реализована, пока её нельзя проверить в runtime; она запланирована на одну из следующих бета-версий. Сохранённая ситуация или `/last` восстанавливает собственное транспортное средство игрока | `UNAVAILABLE` (BI-007) | `player.assign-headless` в [возможности](capabilities.md) |
| Точка входа по идентичности (`/entrypoint:<identity>`) выбирает точную метку, которую показывает OMSI (закрыто статически, BI-001); более поздняя запись с той же меткой выбрана быть не может, как и в собственном диалоге OMSI. Проверка в runtime ожидается | `EXPERIMENTAL` | возможность плана `world.entrypoint-identity` |
| У параметров клавиатуры и контроллеров по ключам (`Environment.Keyboard`, `Environment.Controllers`) нет ключей в каталоге: вместо этого файлы заменяются целиком через `InputSpec` | `UNAVAILABLE` | [launchspec](launchspec.md#inputspec) |
| Кооперативное завершение (`/cooperative-shutdown`, `Behavior.CooperativeShutdown`) включается явно и проверено только офлайн; по умолчанию при завершении сеанса OMSI завершается принудительно, а `ShutdownTimeoutSeconds` не действует | `EXPERIMENTAL` | [CLI](cli.md) |
| Флаги диагностики `/log`, `/omsi-logall`, `/verbose`, `/trace`, `/trace-process` заполняют `DiagnosticsSpec` без дальнейшего эффекта (трассировка хоста в `.omsilaunch\diagnostics` записывается всегда); `/trace-plugin` и `/trace-native` добавляют в неё события трассировки плагина и нативного слоя | `PARTIAL` | [CLI](cli.md) |
| `/runtime-batch`, `/runtime-write-batch`, `/d3d-batch` — тестовые обвязки для проверки | `INTERNAL` | [CLI](cli.md) |

<a id="session-end-and-process-control"></a>
## Завершение сеанса и управление процессом

| Ограничение | Стабильность | Подробности |
| --- | --- | --- |
| Остановка сеанса — это принудительное завершение: `session.stop`, пункт «End session» в трее (завершить сеанс), Ctrl+C и `CloseAsync` приводят к `TerminateProcess`. Процедура завершения OMSI не выполняется, OMSI не перезаписывает `options.cfg` и свои логи при выходе, а любое несохранённое состояние OMSI теряется. Это сделано намеренно: так OMSI не может перезаписать восстановленные файлы. | так задумано | [жизненный цикл сеанса](../concepts/session-lifecycle.md) |
| Кооперативное завершение через WM_CLOSE с тайм-аутом и откатом к принудительному завершению не реализовано | `UNAVAILABLE` (решение по продукту, S-11; в раунде закрытия проверки в runtime OMSI проигнорировал `WM_CLOSE`, отправленный его главному окну) | [статус проверки в runtime](../status/runtime-validation-status.md) |
| При закрытии консоли или выходе из системы у владельца есть бюджет 4 s на остановку и восстановление; всё оставшееся восстанавливается по журналу при следующем запуске | закрытие консоли проверено в runtime; выход из системы не проверялся | [транзакции и восстановление после сбоя](../concepts/transactions-and-recovery.md) |

<a id="transaction-recovery-and-lease"></a>
## Транзакция, восстановление после сбоя и lease

| Ограничение | Стабильность | Подробности |
| --- | --- | --- |
| Аренда установки (lease) — это семафор `Local\`: один владелец на установку **в пределах сеанса входа в систему**; между пользователями не соблюдается; не освобождается, пока другой процесс удерживает дескриптор; любой процесс того же пользователя может удерживать имя | принятый риск (S-18) | [транзакции и восстановление после сбоя](../concepts/transactions-and-recovery.md) |
| Восстановление после сбоя отклоняется (`OL_E_INSTALLATION_BUSY`), пока работает процесс OMSI, записанный в журнал, а для журнала без PID — любой `Omsi.exe` из этого корневого каталога | так задумано | как выше |
| Изначально отсутствовавший путь overlay, содержимое которого изменилось во время сеанса, блокирует восстановление (`OL_E_RECOVERY_ABSENT_OWNERSHIP_MISMATCH`) до ручной проверки | так задумано | как выше |
| Журналы, созданные до появления отпечатков владения, может закрыть только сеанс с идентичными запланированными байтами (`OL_E_RECOVERY_ABSENT_OWNERSHIP_UNVERIFIED`) | `PARTIAL` | как выше |
| Восстанавливаются только пути, которыми владеет сеанс. Собственные записи OMSI во время сеанса (`options.cfg` `[last_map]`, когда ни один параметр не накладывает overlay на `options.cfg`, `Texture\standard.ipr`, кэши, `laststn.osn`, профиль водителя, логи) сохраняются, как после прямого запуска OMSI | так задумано | [транзакции и восстановление после сбоя](../concepts/transactions-and-recovery.md) |
| Удаление устаревшего `closecheck` перед сеансом является окончательным (фиксируется, но не восстанавливается), когда `SuppressStaleClosecheckWarning` равно true | так задумано | как выше |

<a id="runtime-control"></a>
## Runtime-управление

| Ограничение | Стабильность | Подробности |
| --- | --- | --- |
| `weather.set` и `weather.metar.set` записывают исходную запись погоды OMSI (закрыто статически); сохранение значения на такте погоды, определение типа облаков и загрузка METAR ожидают проверки в runtime. Производные значения (влажность, коэффициенты освещённости, фактический ветер) задать нельзя; пока OMSI стоит на паузе, они обновляются только после снятия паузы | `EXPERIMENTAL` | [возможности](capabilities.md) |
| `SetActualDateTime` лишь копирует часы ПК в стартовые часы OMSI (статический анализ); OmsiLaunch его не вызывает и задаёт стартовые часы сам | так задумано | `calendar.set-actual-date-time` |
| Запись строковых переменных, именованные триггеры и звуковые триггеры проходят через собственные методы OMSI (закрыто статически, BI-004); их влияние на скрипты ТС ожидает проверки в runtime. Целями являются только дорожные транспортные средства | `EXPERIMENTAL` | `scripts.string.write`, `scripts.trigger` |
| Нет перемещения ТС, нет пространственной перепривязки между тайлами, нет безопасного для ODE права на изменение трансформации; поля позиции доступны только для чтения | `UNAVAILABLE` (BI-008) | `road-vehicle.read` |
| `camera.lock` / `camera.unlock` требуют PlayerVehicle; у headless-запуска NEW_MAP его нет (его предоставляет сохранённая ситуация) | так задумано (BI-007) | RV-004 |
| Runtime-изменения (`time.set`, `camera.set`, `camera.lock`, `vehicle.variable.set`, spawn, place-random, текстуры D3D) не записываются в журнал и не восстанавливаются | так задумано | [runtime-управление](runtime-control.md) |
| Устаревание handle определяется по собственному никогда не используемому повторно номеру экземпляра OMSI (`IDCode`), а для объектов Human — по исчезновению и повторному созданию; проверено офлайн. Естественное удаление (RV-002: ИИ-автомобили покидают загруженную сеть путей) ещё предстоит наблюдать в runtime, а событие `entity.removed` пока не выдаётся | `PARTIAL` | [runtime-управление](runtime-control.md) |
| Результаты ограничены почтовым ящиком (mailbox) на 64 KiB: длинные списки усекаются (`truncated=true`); данные пикселей ограничены 48 KiB на один `d3d.texture.update` | так задумано | [возможности](capabilities.md) |
| Канал с одним запросом в полёте: один запрос за раз на сеанс; занятый слот даёт `OL_E_RUNTIME_CHANNEL_BUSY`; идентификаторы запросов нельзя использовать повторно | так задумано | [runtime-управление](runtime-control.md) |
| Телеметрия — это кольцо на 64 события: хост, отставший более чем на 64 события, теряет самые старые из них и узнаёт, сколько именно (`telemetry.lost`) | `EXPERIMENTAL` | [постоянный плагин](../concepts/permanent-plugin.md) |
| Хуки устройства Direct3D в модуле — это хуки vtable: на установке, где другой компонент записывает обратно исходные методы устройства (наблюдалось на регрессионной установке вскоре после начала игры), они перестают вызываться и не могут быть сняты при очистке (`OL_E_MODULE_CLEANUP_INCOMPLETE`; компонент остаётся загруженным) | `PARTIAL` | [runtime-модули](../../../reference/runtime-modules.md#native-components-and-hooks) |
| Загрузка runtime-модулей открыта: OmsiLaunch не проверяет, кто создал модуль; он гарантирует лишь, что модули никогда не выполняются внутри процесса OmsiLaunch и что программа сеанса ограничена своей задачей (без второго процесса, завершается вместе с сеансом) | так задумано (E21) | [runtime-модули](../../../reference/runtime-modules.md#security-boundary) |
| Протокол модулей 2 (параметры, активация по умолчанию, файл параметров, программы сеанса, конфликты плагинов, уведомления, `get_value`) проверен только офлайн | `EXPERIMENTAL` | [runtime-модули](../../../reference/runtime-modules.md) |
| Сброс устройства D3D наблюдался в runtime (`resetting`, `restored`, инвалидация поколения); отдельный переход `lost` воспроизвести не удалось, потому что устройство OMSI сразу перешло в `DEVICENOTRESET` | `PARTIAL` (RV-007) | [статус проверки в runtime](../status/runtime-validation-status.md) |
| Runtime-списки выдаются постранично (`cursor`, `limit`, `next_cursor`): страница содержит не более максимального числа строк списка и то, что помещается в runtime-слот на 64 KiB | `EXPERIMENTAL` | [возможности](capabilities.md#pagination) |
| Некоторые расширенные поля графа карты/тайлов/путей/объектов не предоставляются; runtime-читатели — это типизированные снимки, заблокированные проверкой профиля, и никогда не произвольный доступ к памяти | так задумано | [возможности](capabilities.md) |
| Чтение памяти внутри процесса выполняется по схеме «проверка, затем использование» на живом OMSI; одновременное изменение в OMSI между проверкой и чтением может дать несогласованный снимок (`OL_E_RUNTIME_OPERATION_FAILED`) | принятый риск (S-33) | |

<a id="local-control-plane-and-trust-model"></a>
## Локальная плоскость управления и модель доверия

| Ограничение | Стабильность | Подробности |
| --- | --- | --- |
| Модель доверия в пределах одного пользователя: именованный канал (named pipe) (`CurrentUserOnly`), отображения памяти handoff/телеметрии/runtime и семафор lease доступны любому процессу того же пользователя Windows. Такой процесс, прочитав `session_id`, может читать состояние, останавливать сеанс или выполнять runtime-операции. | принятый риск (S-06, S-30) | [локальное управление](local-control.md) |
| Конечная точка управления существует только пока владелец находится в состоянии `Running`; во время запуска и после завершения сеанса клиент получает `OL_E_NO_ACTIVE_SESSION` (выход 4) | так задумано | [локальное управление](local-control.md) |
| Если имя pipe уже занято другим процессом, владелец продолжает работу без конечной точки (`ListenFault`), а второй запуск может ошибочно сообщить `OL_E_SESSION_ALREADY_ACTIVE` | принятый риск | [локальное управление](local-control.md) |
| `.omsilaunch\` наследует ACL корневого каталога OMSI; явное управление доступом не применяется | принятый риск (S-31) | [транзакции и восстановление после сбоя](../concepts/transactions-and-recovery.md) |

## Документация

Нормативной документацией этого выпуска являются английские страницы в `docs/`. `docs/localized/<locale>/` содержит переводы тех же страниц `0.1.0-beta4` (см. [`LOCALIZATION-MANIFEST.md`](../../LOCALIZATION-MANIFEST.md)); если перевод расходится с английским текстом, авторитетными являются английский текст и код. Перечисленные там исторические и устаревшие (legacy) страницы доступны только на английском.

См. также: [возможности](capabilities.md), [статус проверки в runtime](../status/runtime-validation-status.md), [ошибки](errors.md).
